# 最近一次真实选品决策回放

本问题库供 `intake-interview` 的入口 D 使用。目标不是让卖家再填一遍通用问卷，而是按时间线回放一次真实发生过的选品决策，保留当时的候选、依据、拍板理由和用户原话。

## 先选定一次决策

优先选择最近且用户记忆清晰的一次：至少考虑过两个候选，并对其中一个作出过 `accepted`、`rejected` 或 `watchlist` 决定。如果用户无法把不同时期的决策分开，暂停结构化写盘，先确认时间边界。

## 一、决策现场

1. 这次选品大约发生在什么时间？无法确定日期时记为 `unknown`，不猜。
2. 当时要做的平台、站点、类目和业务目标是什么？
3. 是什么触发了这次选品：市场信号、供应链机会、库存空档、老板指定，还是其他原因？
4. 当时必须遵守的资金、物流、合规、时间和团队约束是什么？

## 二、当时真正看过的数据

对每个工具或文件分开询问：

| 问题 | 记录字段 | 纪律 |
|---|---|---|
| 当时用了哪些工具或原始报表？ | `tools_or_sources` | 工具名不等于事实来源，尽量追到原报表 |
| 具体看了哪个指标？ | `metrics_considered` | 记录站点、时间窗口和口径；缺少就标记待核实 |
| 原始导出、截图或报告现在还在吗？ | `evidence_locator` | 只记安全的本地别名或相对路径，不记密钥、Cookie、真实 MCP 地址 |
| 这是现在能打开的材料，还是凭回忆口述？ | `evidence_status` | `documented` / `recalled` / `mixed` |

`recalled` 表示事后回忆。例如“当时 CPC 大概 3 美元”可保留为用户原话，但不得进入事实数字、硬过滤、精确毛利或评分。后续拿到原始报表时，仍需按 `verified_import` 流程验证，不因为用户记得很确定就升级为事实。

## 三、逐候选回放

每个候选品单独记录，不把多个品压成一条总结：

1. 候选品名、ASIN/链接/当时使用的别名是什么？
2. 它当时为什么会进入候选？
3. **当时**的决定是 `accepted`、`rejected` 还是 `watchlist`？
4. 你当时是怎么说的？尽量保留原话，不用现在的解释替换。
5. 哪些数据、能力、红线或偏好真正影响了这个决定？
6. 如果当时只能再补一项数据，你最想补什么？

## 四、后来结果

后来结果必须与当时决定分开询问和写盘：

1. 这个品后来是否上架或打样？状态记为 `not_launched` / `launched_pending` / `profitable` / `unprofitable` / `stopped` / `unknown`。
2. 截至什么日期能观察到什么结果？
3. 结果是有领星/平台/财务报表可核验，还是只凭回忆？
4. 现在回看，你会保留当时规则，还是只把它列为待确认的 SOP/learned 候选？

后来亏损不得把当时的 `accepted` 改写为 `rejected`；后来走红也不得把当时的 `rejected` 改写为 `accepted`。这两类信息回答的是不同问题。

## 五、写盘前确认

写盘前展示两张表：

1. **画像/SOP 候选表**：字段、候选值、来源原话、`documented/recalled/inferred`、是否待确认。
2. **决策日志表**：每个候选品一行，分别列出当时决定、当时原话、依据状态、后来结果、后来结果依据状态。

用户确认后：

- 画像与 SOP 按 `intake-interview` 的既有边界处理；
- 每个候选品通过 `recommendation-review` 写入独立决策文件，并标记 `来源类型: historical_retrospective`；
- 无原始报告时明确写“无（历史复盘）”，不伪造报告路径；
- 任何 `recalled` 数字只保留在原话或备注中，并标记“需人工核实”。
